# Plan v2: fence at parity with Anthropic's sandbox-runtime (srt)

Sources: Toolroll `~/Developer/so-access` @ af114bca (0.9.69 candidate); srt @ c66fb77 (v0.0.81).
Citations: `af:` src/agent-fence.ts, `inv:` src/invoke.ts, `mac:` / `lin:` / `mgr:` / `su:` srt's src/sandbox/{macos-sandbox-utils, linux-sandbox-utils, sandbox-manager, sandbox-utils}.ts, `seccomp.c` srt's vendor/seccomp-src/seccomp-unix-block.c.
Inputs: v1 of this plan, the Codex review of v1 (findings 1–12, all folded in below and tagged [C#]), and the owner's binding decision.

## As shipped in 0.9.70: built on srt itself (owner decision, 2026-10-24)

The owner changed direction mid-build: "match the Anthropic standard one and don't overcomplicate it". 0.9.70
depends on `@anthropic-ai/sandbox-runtime` **0.0.79** (pinned exactly; published 2026-10-07, the newest at least two
weeks old) and every macOS Seatbelt profile and Linux bubblewrap + seccomp command is generated by its own code per
launch. Everything below this section is the plan as first written and the C1–C12 build; where it describes a
hand-written mechanism (C5's baseline, C6/C7's bubblewrap and seccomp, C8's protected-name walk, watch and
quarantine, the write unlocks, the Linux launch-folder root), that mechanism is gone.

**How it is called.** `src/agent-fence.ts srtTermsOf` turns a launch's fence into srt's own config
(`readConfig.denyOnly/allowWithinDeny`, `writeConfig.allowOnly/denyWithinAllow`, `allowMachLookup`, the proxy port and
credential). macOS: `wrapCommandWithSandboxMacOS` (deep import; the package has no `exports` map) runs in-process with
the working folder set to the launch's for the call (srt anchors its mandatory denies at `process.cwd()`). Linux:
`wrapCommandWithSandboxLinux` is asynchronous, cwd-anchored and leaves bwrap mount points to clean up, so each launch
runs through `src/sandbox-launch.ts`, a helper process that changes into the launch's folder, starts srt's socat relays
(`initializeLinuxNetworkBridge`) to the run's proxy when the network is confined, runs srt's command, forwards signals,
and calls `cleanupBwrapMountPoints` after. The command first writes one byte to a descriptor of its own before the
launch starts: a sandbox whose setup failed (bubblewrap couldn't mount over another launch's folder that vanished after
srt looked, on a read-only root) never ran the launch, so it is set up again from a fresh look, up to three times; a
launch that started is never re-run. Availability (fail closed) is checked before every launch:
`sandboxRuntimeProblem` (macOS: sandbox-exec works; Linux: srt's `checkLinuxDependencies` with no errors, its seccomp
helper present, ripgrep installed, and an unprivileged bwrap probe).

**What Toolroll adds (static rules in srt's config):** Toolroll's state folder (less the checkout pool) and database
denied read+write; `~/.toolroll`; other launches' private folders unread by pattern (written: those there at launch);
the build's own checkout writable; other tasks' checkouts read, never written (those there at launch); under policy v1
the home configuration denied by name and a sign-ins check's exact files read again; the project's `readDeny`; the
project's `machLookup` (validated, MACH_NEVER denylist); flows' scratch folders denied; the run's proxy (port and
credential; our proxy now accepts any user name with the run's secret, as srt puts its own name there) and its tool
broker on srt's second relay (macOS: srt's `socksProxyPort` slot; Linux: the relay's port 1080, which Claude's tool
list is rewritten to).

**Kept beside srt (static, per the security review):** Toolroll's own install, the sandbox-runtime package, the
launch helper and the Node running them are read-only to every launch (`toolrollInstall`, write-denied through
`denyWithinAllow`); and the handoff refuses a result that adds or changes a protected name (`protectedChanges`: a
superset of srt's DANGEROUS_FILES and dangerous directories, plus `.envrc`, `.npmrc`, `.yarnrc`, `.yarnrc.yml`,
Claude's settings files and `.git/config`), because srt holds those names only as they are when a launch starts. With
write unlocks gone there is nothing to exempt.

**Dropped:** the hand-written Seatbelt baseline and network rules; our bubblewrap command, host-socket masks, private
/tmp and launch-folder root; the vendored seccomp helper, its build, manifest and CI/publish jobs; the protected-name
walk, watch and quarantine (srt's mandatory denies are what hold); write unlocks (srt can't re-allow
a write inside its mandatory denies: the `writeUnlock` field, setting and `--unlock` are gone); Q-B's extra names and
home persistence denies (not in srt's list); run-folder regex fences in Seatbelt (now an srt glob read deny).

**Accepted srt limits:** rules fixed at launch; on Linux a deny's glob is expanded at launch; shared temp
(`/tmp/claude` unless the launch's own) between concurrent builds; reads open by default (v2); directory metadata;
same-sandbox task ports; Launch Services lookups (listing apps; opening one stays refused); KERN_PROCARGS2 (another
process's arguments and environment, a tool server's secrets among them) readable on macOS; under an open network
unix sockets are unrestricted on macOS; srt's Linux filter refuses unix sockets and io_uring but not a VM socket or a
user namespace; srt can't write back inside a write deny, so a folder or checkout made after launch inside a written
area is writable, an own checkout can be removed, and under policy v1 a sign-ins check can't write its transcripts;
a granted folder can be removed (the next launch never grants it through a link).

## 0. What changed from v1

- **The target is now parity with srt, in both directions.** Where srt is stronger, we adopt it. Where we're stricter than srt in ways that block features, we relax to srt.
- **Toolroll keeps only the isolation srt has no concept of, and only where it protects Toolroll's own integrity:**
  - its state;
  - other runs and other tasks;
  - the approval-sealed per-run network;
  - its own install.
- **Phase 1 (0.9.70) hardens the current engine to the srt baseline.** That hardened engine becomes the comparison baseline [C, recommendation].
- **The srt backend becomes a gated prototype** with:
  - one exact revision and an extraction manifest [C11];
  - an async prepared-launch boundary [C9];
  - typed permissions instead of free-form SBPL/argv hooks [C4];
  - engine, policy and helper pinned per attempt [C8].
- **v1's "six small patches" estimate is withdrawn.**
- **The openat sign-in helper is dropped.** Sign-ins become direct read grants evaluated by the sandbox itself, so nothing privileged reads or copies a sign-in file (§1.3).

### 1.2 Relax to srt (stricter today, and it blocks features)

- **Home reads open by default.**
  - Drop the default by-name read denies: `HOME_CONFIGURATION` (af:220), `homeNames` (af:250), and Claude's file-tool home rules.
  - Projects get an opt-in, approval-sealed `readDeny` list. This is srt's `denyRead`.
- **Reads of sibling repositories and of the project's primary working tree open.** Today `taskBoundary` denies both (af:265–292).
- **Same-sandbox process interactions as srt does them.**
  - Allowed within the same sandbox: `process-info*`, `signal`, `mach-priv-task-port` (mac:1091–1093).
  - Toolroll denies the task port entirely today (af:867). Relax.
  - *As built (0.9.70):* relaxed where srt has it — only commands share a sandbox there. Where Toolroll runs the agent harness itself inside the sandbox (Claude, Gemini and ACP builds), the harness holds its provider sign-in in memory (Node is signed with `get-task-allow`), so those launches keep the deny. No Toolroll secret holder shares a build's sandbox: each tool server is its own `sandbox-exec`; the broker, egress proxy and scout browser run outside. Measured: an unentitled process gets no task port even unsandboxed (`task_for_pid` → KERN_FAILURE), and `lldb` attach failed inside a same-sandbox-allow profile.
  - `kern.procargs` stays unreadable. It isn't on srt's sysctl allowlist either.
- **Directory metadata:** accept srt's `(allow file-read-metadata (vnode-type DIRECTORY))` (mac:929). Q7 is decided, which overrides Codex's "patch it".
- **Sign-ins level returns, srt-style (§1.3).**

### 1.3 How sign-ins work, and why there's no helper

- The check reads its exact sign-in files itself, through the sandbox:
  - `~/.claude.json`, `~/.claude/settings.json`, and on Linux `~/.claude/.credentials.json`;
  - `~/.config/gh/{hosts,config}.yml`;
  - `~/.codex/{config.toml,auth.json}`.
- The kernel resolves those paths *inside* the sandbox's view. A link planted at a sign-in name and pointing into Toolroll's state resolves to a denied path:
  - Seatbelt checks the resolved vnode's path;
  - bwrap resolves it within its mount namespace, where the state is masked.
- **So the read is safe by construction.** No privileged read happens and no copies are made. `readGrantedFile` (af:1145), the Codex home copy (inv:1256–1261), `sign-in-copies` and `signInCopiesRoot` (af:1184) are all removed.
- **The openat helper is unnecessary, because nothing copies any more.** The privileged-copy race behind Codex's [C6] protocol concerns no longer exists. Builds keep their own provider-home linking (provider-home.ts:76), which is unchanged and is not a sign-in read.
- With home reads open, a plain **sandboxed** check can already read these files unless the project's `readDeny` covers them. The check-access words must say so plainly.
- **What "sign-ins" adds:**
  - It pierces `readDeny` for exactly those files: Seatbelt `literal` allows after the deny on macOS; on Linux, masking the siblings one by one rather than binding by path, so nothing is bound from a path that might be swapped.
  - It grants writes to Claude's transcript `.jsonl` files on macOS, as before (af:855–858).
  - It grants writes to measured Codex `sessions`/`log` folders, never `config.toml`.
  - `CODEX_HOME`, `GH_CONFIG_DIR` and `XDG_CONFIG_HOME` point at the real folders.
- **Residual on Linux:** a sibling created after launch inside a `readDeny` folder that was pierced stays readable until the next launch. That's the same residual `flattened` has today (af:728–740).

### 1.5 Policy versions and approvals

- **The fence policy version becomes part of the sealed execution profile.**
  - Opening home reads is a widening, so it applies only to scopes sealed at **v2**.
  - Approvals sealed before 0.9.70 keep v1's home denies ("approvals mean exactly this").
  - Narrowings apply to every version: deny-default, Apple Events, seccomp, mandatory write denies, persistence denies.
- **Pinned per attempt [C8]:**
  - policy version and digest;
  - engine;
  - method;
  - helper sha256;
  - effective grants.
- The fence probe, the isolation probe, the workload, lazily started tool servers (inv:407, tool-broker.ts:148) and cleanup all use that pinned context.

## 2. Phase 1: 0.9.70 on the current engine

- the same action succeeds unsandboxed and is refused sandboxed;
- a native test that skips (harness.ts:104) doesn't count as release evidence [C10, recommendation].

The release lane runs on a macOS runner and a Linux runner that have the prerequisites.

**C7. Seccomp helper (corrected P6) [C3, C2].**
- Vendor `vendor/seccomp-src/{seccomp-unix-block.c,apply-seccomp.c}` and build script `vendor/seccomp/build.ts` from c66fb77 (Apache-2.0). Build static x64 and arm64 binaries in release CI.
- **Filter = all upstream rules except `socket(AF_UNIX)`:** AF_VSOCK, the three io_uring calls, and the stacked namespaces/mount filter.
- Toolroll's private `/tmp`, keep paths and `linuxHostSockets` masks stay (af:983–1004). That's what keeps host sockets out of reach, by masking known socket locations; it is not a general path allowlist.
- **Ordering:** `bwrap … node forwarder <bridge> -- apply-seccomp <cmd>`. The forwarder opens unix sockets per connection (egress-bridge.ts:29), so it sits outside the filter; only the workload is filtered.
- **Helper trust:**
  - copied at install into `<state>/helpers/` (mode 0700, inside the fenced state);
  - sha256 checked against the manifest right before every launch;
  - exec'd by that exact path;
  - no search fallback (generate-seccomp-filter.ts:239 is not used).
- A missing helper or a mismatched hash means no Linux fence, so the existing refusals apply.
- *Tests (native, positive control):* `io_uring_setup`, `socket(AF_VSOCK)` and `unshare(CLONE_NEWUSER)` succeed unsandboxed and fail with EPERM sandboxed; a replaced helper means refusal; the bridge still carries proxy traffic.
- *As built (0.9.70):* `vendor/seccomp/build.mjs` (not .ts: no TS toolchain needed on the runner); `publish.yml` builds x64 and arm64 on their own runners (`seccomp helper · linux-<arch>`, release tag checks) and the package ships both in `dist/helpers/` with `manifest.json`; `ci.yml` gains `linux fence · bubblewrap + seccomp` (required PR check) running the attack suite with `TOOLROLL_REQUIRE_NATIVE=linux`, so a skipped Linux attack fails the lane. The helper reaches the launch as `FenceGrants.seccomp` from `fenceFor`, is re-hashed in `linuxFenced` right before the spawn, bound read-only at its own path, and `SRT_*` switches are unset. Risk: a machine whose bwrap works but forbids the helper's nested user namespace has no Linux fence (fail closed).

**C8. Mandatory write denies plus persistence (Q3, Q4).**
- srt's DANGEROUS_FILES and directories, `.git/hooks` and `.git/config` are applied:
  - in every mode, anchored at the checkout;
  - under `writes: anywhere`, also anchored at home, where shell rc files and `.gitconfig` are the persistence points srt's list names;
  - to Codex's profile as deny entries too.
- A linked worktree's shared Git directory stays under the trusted-binding rules (af:435) [C4].
- **Unlock (Q3):** an exact relative file list sealed in the execution profile and bound by its digest; siblings stay denied. Mandatory denies are emitted after grants except for unlocked exact files.
- **Linux, absent names:**
  - existing names are bound read-only;
  - for names that don't exist yet, **no placeholder mounts in Phase 1**, because of the shared-lifecycle hazard [C1]. Instead the handoff refuses a result that created a denied name it wasn't unlocked for.
  - Residual: that file exists in the checkout during the run.
- *Tests:*
  - writes to `.mcp.json`, `.vscode/tasks.json`, `.git/hooks/x` and, under anywhere, `~/.zshrc` are refused natively;
  - an unlocked exact file is writable and its sibling isn't;
  - the Linux handoff refuses.
- **Flag:** srt's list doesn't include `~/Library/LaunchAgents`, systemd user units, `.claude/settings*.json` or `.envrc`. Matching srt means those stay writable under anywhere. Owner Q-B.
- *As built (0.9.70):* owner Q-B: added. Also added, because unfenced Toolroll processes run these tools and trust their user configuration: `.npmrc`, `.yarnrc`, `.yarnrc.yml` (any depth), and at home `~/.config/git`, `~/.config/gh`, `~/.config/pip`, `~/.pip`. Seatbelt matches every depth and either case; bubblewrap and Codex bind/list what exists at launch, found by a bounded walk (20k entries, depth 8, no `node_modules`, no links); everything else is refused at the handoff (`protectedChanges` in `builder.ts commit`, all platforms). The bound repository's own `.git/config`, `.git/hooks` and the worktree's `config` are denied by path. `writeUnlock` is the profile field (exact relative files, validated, sorted); its project setting arrives with C9. An unlocked name is given back only as itself (`unlockSafe`: no link at it or above it in the checkout, one name only, real path = lexical path), re-checked right before a bubblewrap bind, never over a denied or read-only path. Every fenced launch form (an agent, its setup and check commands, a saved result's checks, a flow's setup and script) runs under one watch (`withProtectedWatch`): a snapshot of the protected names absent at launch (checkout any depth, home) and of protected names that are links, compared after the launch; anything made or re-pointed fails the launch, and inside the checkout is moved (by rename: a link moves as the link) into `<state>/quarantine/`; at home it is left in place and said, because it could be the person's own file made meanwhile. Pre-denial by placeholders was not chosen: a placeholder bwrap creates on the host outlives the launch (the shared-lifecycle hazard) and at home would itself change the person's setup (an empty `~/.bash_profile` shadows `~/.profile`); in workspace mode the home folder is read-only anyway, so this matters only under `writes: anywhere`. Unlocks are filtered once for every backend (`grantableUnlocks`: safe name, never inside a fenced, read-only or pooled path, only where writes reach). bubblewrap never binds through a protected link (a mount follows a link, so the name itself can't be masked): a link leading somewhere the build can't write needs nothing; one leading to a regular file or folder inside the checkout has that target bound read-only; anything else (a target it could write elsewhere, a dangling link it could fill) refuses the Linux launch, naming it; nothing inside a fenced or pooled path is ever bound (Codex likewise never lists a path inside a denied one). The watch fails closed: a checkout it can't walk whole before or after the launch counts as changed; a protected link is recorded with what it says and the identity of what it leads to (dev:ino or dangling), and any change fails the launch; a made name is moved only when every folder from the checkout to it is a real folder (never renamed through a link), otherwise left and said. The walk below the checkout must see all of it (200k entries, depth 32, `node_modules` skipped as no tool reads configuration from there): a checkout it can't see whole has no Linux fence and Codex refuses it. Submodules' config and hooks (`.git/modules`) are denied with the repository's own. Residual: a coding session (a long-lived Codex app-server) isn't under the per-launch watch; its existing protected names are read-only in its profile. Toolroll's install (this package's folder, the Node running it and that Node's prefix) joins every launch's read-only grants (Q4).

## 5. Phase 3: parity gate. Phase 4: flip.

**Phase 3 (parity gate):**
- The baseline is the **hardened Phase-1 legacy engine**.
- The probe matrix covers:
  - filesystem: read, write, stat, list, rename, create, exec;
  - **syscall and IPC probes:** sockets, mach lookups, Apple Events, procargs, io_uring, userns, ptrace;
  - concurrent runs;
  - hostile path spellings: `[`, `*`, case folding, trailing slash;
  - helper replacement, incomplete scans, late-created paths.
- Both engines run the attack and slow suites natively, with positive controls; skips fail the gate.
- Any difference must be srt-stronger or on the owner-accepted list (task port, directory metadata).

**Phase 4 (flip):**
- macOS first, then Linux, when each platform's gate passes.
- The engine is pinned per attempt. Switching affects new attempts only, after draining.
- An engine refuses a policy version it can't enforce. Because Phase 1 puts every narrowing into legacy too, rollback never re-widens.
- Legacy is deleted on evidence (compatibility plus a rollback window with no incidents), not on a release count [C, migration].

**Deferred:**
- Q6, Codex as a whole process under srt [C7]. It needs a design that keeps harness credentials and network separate from command execution.
