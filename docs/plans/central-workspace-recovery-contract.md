# Recovery for an enrolled central workspace

Status: proposed CW2 policy, revised after independent review, 20 November 2026. Documentation only; no restore, startup, credentials or live settings change. CW1 metadata remains disabled and is not recovery-ready. This contract follows `central-workspace.md` and the execution contract. Source inventory describes existing behavior; the enrollment root, exclusion protocol and retirement manifest below are proposed boundaries requiring review.

## Scope and invariant

**Never-enrolled personal installations keep the existing 0.9.116 restore behavior.** No new password, SSO suspension, backup refusal or startup lock is imposed on that path. Presence of CW1's ubiquitous `workspace_identity` row does not enroll an installation. Its absence does not establish personal status either.

A person explicitly enrolls an installation for central recovery before remote TUI access can be enabled. For that installation, a restored backup may recover history but cannot resurrect authority revoked since the backup. The stable lowercase UUIDv4 `workspaceId` survives an admitted same-workspace restore; a fresh opaque 32-character lowercase hex `recoveryGeneration` fences each recovery. Neither field substitutes for retiring actual credentials and standing execution permissions. Central capabilities stay false until the complete applicable retirement and startup protocol is implemented, independently reviewed and proved.

The first supported central recovery ceremony is a stopped, co-located operator operation. No remote restore endpoint, arbitrary SSH, new shared-secret recovery API or device dispatch is introduced. General SSO-only recovery and automatic cross-installation/legacy import are deferred; these restrictions concern central enrollment/recovery only.

## Existing restore and protection seams

`src/backup.ts:restoreDatabase` currently validates a plain copied backup, WAL state, quick check, supported schema (oldest 103), ledger and a migration probe. It saves the current database, rechecks `runningNow`, carries current Flexible sign-in addresses, migrates the stage and calls `resetFlexibleSignInsForRestore` in a transaction. It folds journals and renames the stage into place. The test-only `afterPublish` seam precedes the final open; a failed final open copies the saved database back. Preserve this personal path unchanged.

`runningNow` checks backup/watch leases and runner freshness; it is not universal process-exit proof. `console-instance.ts` proves a live console using a database instance secret and challenge. `runner-process.ts` supplies protected process records and PID-birth/host evidence. `deploy-lock.ts` uses a separate owner-only SQLite coordination lock whose inode must not be replaced. None is a shipped all-writer restore exclusion protocol.

`login-secrets.ts` establishes the agent-denied, owner-private `.toolroll-secrets` boundary beside the real database, including no-symlink/ownership checks. `laptop-service.ts` pins a canonical database path, absolute command, service definition and digest; launchd/systemd unit generation is a useful service-binding seam. `up-processes.ts` explicitly permits trusted console and worker processes sharing that database and nearby secret files. These are reusable conventions, **not evidence of an existing enrollment expectation root or immutable service manifest**.

## Enrollment cannot be inferred from a restored database

Proposed trusted records, outside every database backup:

- **Expectation registry:** an owner-protected installation registry in a fixed product-owned configuration location, independent of the database folder. A monotonic entry binds a random installation ID to the canonical state/database path, stable workspace ID, protocol version and enrolled-service identities. States are `enrolling`, `enrolled`, `recovery-blocked`; ordinary restore/uninstall cannot erase the entry. It contains no bearer secrets. It is not read from a checkout, environment flag, request parameter or database marker.
- **Service expectation binding:** installed service definitions and protected launcher profiles pin that installation ID, registry location/version and `centralRecoveryRequired` state. A central invocation requires the registry; it cannot fall back to personal if a root is missing. Direct commands consult the registry by canonical database path before opening for live use. A caller supplying an unenrolled-looking DB cannot override a registered path's expectation.
- **Recovery root:** inside the protected state secret boundary, binds installation/workspace IDs, canonical state identity, committed recovery generation, schema/manifest version and pending transaction. An intent binds exact old/staged/installed database identities, retirement manifest digest and phase. An additive DB enrollment receipt records those nonsecret IDs and protocol/manifest version: its presence requires an admitted root, but its absence never cancels an outside expectation. No password, provider secret or token value is recorded.

The registry path, secure cross-platform atomic publication/ownership policy, launcher binding and shared-lock mechanics are **new design choices, not audited existing facilities**. They need a focused filesystem/service threat review before integration. The registry must remain discoverable when the state folder/root is absent; putting the sole expectation next to the DB does not meet this contract. A checksum in the DB, root-only consistency check, or a freely removable flag is insufficient. The protection target is rollback/copy/crash and build-agent writes, not a malicious OS owner deleting all product state, registry and service definitions. That administrative destruction is a reinstall/trust reset, never continuity of the old central plane.

| State at invocation | Required classification and action |
| --- | --- |
| No registry entry, no central service/profile expectation, ordinary legacy personal invocation | Never enrolled: existing personal restore/start behavior. No central capability is conferred by metadata. Missing global registry may retain this classification only when no protected central expectation exists |
| Healthy personal installation explicitly enrolls | Actual local operator ceremony; stop/exclude prior processes; identify current DB/workspace; validate writer/retirement coverage. Write durable `enrolling` expectation and service binding **before** publishing root/DB enrollment. Complete both and mark enrolled only after readback. Crash after expectation creation is blocked, not personal |
| Registry says enrolled/enrolling but root missing, corrupt or mismatched | Recovery-blocked. Preserve files; explain local repair/reproof. Never mint a replacement root or infer personal from DB/schema |
| Central service/profile requires enrollment but registry missing/corrupt | Recovery-blocked before DB access/listen/dispatch. Reinstall must not silently remove that requirement |
| Root present but expectation missing, or DB claims enrollment without an admitted binding | Unadmitted/copy evidence: no central service. Explicit reconciliation required; do not auto-adopt root or fall back to personal for this state |
| Registered path contains a rolled-back pre-enrollment or pre-identity DB | Still enrolled by registry. Ordinary personal restore cannot replace it. Central restore refuses before migration/publish unless separately reviewed identity admission exists; retain current DB and offer explicit data-only import/recovery path |
| Copied/foreign DB at registered path, or root/service/workspace IDs disagree | Block. Stable IDs alone cannot admit a clone or move. No second active old plane is assumed safe |
| Copy to a new installation/path | Not a newly trusted central plane. Explicit offline import/enrollment with fresh credentials and proof old plane retired is needed; until designed, refuse central adoption. A copied enrolled DB receipt without its registry binding blocks even an ordinary invocation. A pre-enrollment copy at an unregistered path is indistinguishable from a legitimate personal backup; this contract cannot detect that from DB contents. It confers no central continuity or safety claim. A deliberate personal data import must not silently preserve connected authority |
| Reinstall with registry/service expectation intact | Preserve installation identity and requirement; inspect root/DB pair. Missing root stays blocked. Do not initialize a personal root |
| Loss of all trusted enrollment records | No automatic central continuity or credential restoration. New installation plus reviewed data-only import/re-enrollment; operator is told old credentials/plane require separate retirement |

An explicit central enrollment command must refuse if it cannot install a durable independent expectation or prove the necessary startup/writer coverage. Password-capable local operator is the proposed first supported enrollment/recovery proof. An SSO-only personal installation remains usable and restorable as today; central enrollment stays unavailable until its separately reviewed ceremony exists. No universal new-password or SSO product policy follows from CW2.

## Applicable authority manifest

Before central enrollment, publish a closed manifest covering **every verifier and every persisted permission that can accept, dispatch, settle or publish work** in that installation's supported schema. Each entry records owner module, concrete tables/protected references, verifier, staged retirement operation, postcondition query, count and any outstanding custody. Schema/version and manifest digest are bound in the stage and intent. Unknown or unimplemented entries prevent central enablement; a partial manifest cannot be labelled complete. The following is the minimum source-grounded inventory, not proof that all helpers already exist.

| Class and existing verifier/owner | Enrolled restore requirement |
| --- | --- |
| All `credential` kinds: person API/MCP, lead and coordinator (`api-tokens.ts`, `server/guards.ts:identify`, `operate-remote.ts`, `Store.leadFor`, `coordinator.ts`) | Revoke every restored credential. Ordinary API/lead/coordinator credentials are not all mint-account-generation bound; fresh requests can use a restored secret even after an account-generation bump. Record pending proposal retirement |
| Inbound MCP OAuth (`mcp-oauth.ts`, `oauth_grant`, `oauth_refresh`, `oauth_code`) | Revoke backing credentials; consume codes and retire access/refresh/grant renewal authority. Backups roll grant/account generations and refresh reuse history back together. Public `oauth_client` registration metadata can remain |
| Browser/local-owner (`server/session.ts`, `web_session`, local-mode standing) | Remove durable sessions; restart with empty memory maps for links/nonces/SSO visits/OAuth requests. Retire old local-mode generations and approval standing; no restored loopback link becomes full authority |
| Password/CLI remembered secret (`scope.ts:authenticateAccount`, `approver`, `login-secrets.ts`) | Do not serve restored password hashes. Carry only a freshly reproved current recovery operator with fresh generation/new secret not matching current or restored hash; suspend other restored accounts pending readmission. Retain/report stale saved-login files safely; never use an unsafe deletion to fix them |
| SSO membership/provisioning (`sso-settings.ts`, `sso_identity`, `Store.signInWithSso`) | Hold restored SSO admission and auto-provision until explicit membership reconciliation. Preserve subject tombstones; deleting links can allow a removed person to provision afresh. Protected `sign-in.json` is not a restored-membership proof |
| Paired chat, action/confirmation/pairing, invitations and push (`Store.revokeDerivedAuthority`, chat provider helpers, `chat-approval.ts`, push modules) | Revoke restored derived authority and consume pending one-use authority; preserve messages and history. Include inbound platform callbacks, not merely browser cookies |
| Flexible sign-ins/thread authority (`flexible-sign-in.ts:resetFlexibleSignInsForRestore`, `endThreadAuthorityFor`, protected tool-secret references) | Keep existing carried-address retirement and removal epochs; end restored authority. Retiring DB rows does not prove a remote native process stopped or remove every protected secret |
| Runner/watch/claim/native custody (`runner.ts`, store claims/leases, `runner-process.ts`) | Retire credentials and attempt/lease standing; preserve unresolved stop/side-effect custody as unknown. No automatic failover/requeue from old heartbeat, generation rotation or silence |
| Pending approvals and unattended execution/publication (`approval-authority.ts`, `approval-policy.ts`, modes, release approval, task/plan intake, repair/follow-through, schedules) | Explicitly hold/withdraw executable standing, approvals, pending release/deploy/publication permission and resumed work. Preserve historical ledger, results and actual check provenance. Fresh operator login must not restart them |
| Public intake/platform hooks/flow triggers (`server/remote-hooks.ts`, `flow-triggers.ts`, intake grants, pending external delivery/replay state) | Hold restored admissions, schedules and deliveries until current re-admission. Secret addresses/platform headers outside person API auth must not bypass recovery |
| Provider/tool secrets and outbound OAuth (`keys.ts`, `tool-secret-store.ts`, `oauth-run-token.ts`) | Do not blindly copy/delete external secrets. Hold restored task/tool standing referring to them; explicitly revalidate connections before dispatch. Inbound retirement does not revoke external provider access |
| Future central read/device/transfer/attempt protocol | Bind issuance/use to committed generation; retire profile/enrollment/transfer/lease/result settlement standing. Reject stale attempt settlement even if output upload completed |

`revokeDerivedAuthority` and `resetAccountPassword` intentionally preserve ordinary API/MCP/coordinator credentials in password rotation; they are not complete restore sanitizers. Do not change their personal behavior. `withdrawApproval` and existing narrowing helpers are candidates for manifest entries; exact persisted fields and background consumers must be audited before that entry can pass. The broad execution/trigger inventory is currently **not closed**, so the integration/enablement gate remains blocked.

## All startup, ingress and dispatch guards

For enrolled installations, a shared admission check must run before any live store use, listener, credential acceptance, background dispatch or cached session resurrection. A request-only check on `/engine/connection` is insufficient. Required integration points are:

1. `store.ts:openStore` / `openStoreReadOnly` admission contract: trusted expectation classification precedes migrations/live use. Explicit offline staged handles are branded/internal, never ordinary live handles. A stage may not create or repair an expectation by opening.
2. `cli.ts:main` / live store opens and `operate.ts` entry paths: direct CLI, `serve`, `watch`, `up`, backup restore, release/deploy, and protected password/account operations use that admission. A restored password or a direct runner command cannot bypass the service launcher. Read-only central access is also guarded.
3. `operate.ts:runUpRole` and `up-role-child.ts` / controller and service starts: console and worker validate the same committed pair before role startup; `laptop-service.ts`, `daemon.ts`, controller startup and supported direct starts bind the same expectation. Preserve multiple trusted co-located writers under shared participation.
4. `serve.ts:createDecisionServer` before `createServer`/startup background work: cover every route, browser sign-in/SSO/password bearer, ordinary API, OAuth registration/code/token, MCP HTTP (`mcp-http.ts`), SSE/live streams, terminal upgrade (`terminals.ts`), public hooks/forms/platform callbacks (`server/remote-hooks.ts`) and local-owner access. Existing authenticated connections cannot survive a restore transition.
5. `mcp.ts:serveMcp`: stdio is a separate ingress, guarded before accepting commands; HTTP MCP is covered by server and checked store admission.
6. Runner/auth/claim/heartbeat/start/result and worker background loops (`runner.ts`, `operate.ts` worker/watch paths), scheduler/trigger/chat/intake upkeep and release/publication transitions: retain shared admission through use; transaction-level generation/current-authority checks prevent stale settlement. Guarding only registration is insufficient.

The module list is a concrete integration audit queue, not a claim each call site has a gate today. Enrollment cannot ship until static call-site inventory and isolated native starts prove no supported live entry bypasses it. No new agent runtime limits are introduced.

Proposed exclusion: all participating live processes retain shared admission; stopped restore holds exclusive admission across recheck, preparation and publication. Trusted co-located writers remain supported. Reuse the separate SQLite-lock pattern only after reviewing one process-wide manager and POSIX descriptor semantics; closing duplicate descriptors must not drop protection. Never unlink/replace its inode. Prove legacy/nonparticipating console/worker/process identities gone using protected custody and actual process identity, not lease expiry, PID alone or closed port. If complete exclusion cannot be established, enrollment/restore refuses. **The exact root/lock implementation is unresolved and blocks integration.** Schema compatibility must also make unsupported older binaries refuse work; metadata alone cannot constrain an old binary.

## Enrolled restore ordering and crash recovery

Only after the preceding contracts pass, extend the existing stopped restore ceremony for enrolled installations. Require an actual local terminal, no remote/lead/coordinator proof, and a current unrestricted password-capable operator; reuse hidden proof conventions from `passwordResetCommand`, not its intentionally narrower invalidation semantics. Bind proof to installation, backup fingerprint, operator generation and manifest. Shared secrets or caller-supplied `approved: true` cannot construct the internal proof.

1. Under exclusive admission, prove old process exit and current operator. Validate same-workspace backup before migration; unsupported pre-identity/foreign backup leaves current installation untouched.
2. Save current DB as today; persist/fsync `prepared` intent with exact file identities, new generation and manifest version. Until intent publication, failure leaves the old active pair unchanged.
3. On the unreachable stage, perform the entire applicable retirement/holds, operator replacement, fresh generation and ledger/manifest in one transaction. Preserve history and unknown custody. Close/checkpoint/reopen and verify every manifest postcondition. Failure retains the old DB and failed-stage evidence; never serve a partly retired stage.
4. Persist `publishing`, recheck proof/lock/old identity and rename only the verified stage. Persist/read back `published`. Startup remains blocked throughout.
5. Commit root to the exact new DB/generation/manifest, fsync/read back, then mark transaction committed and release exclusion. Fresh sign-in is separate; no old cookie/device/runner is automatically re-enrolled.

Crash before publication can cancel/resume only after matching old DB readback and local reproof. During/after publication, commit only the exact verified sanitized stage; mismatch stays blocked. Rollback is a new prepared retirement of the saved DB under the same barrier and another fresh generation, not silent authority resurrection. Preserve all copies and original failures. This modifies enrolled restoration only; existing personal `afterPublish` fallback stays unchanged. Do not claim protection against a second independently running cloned installation; migration/adoption needs explicit old-plane retirement proof.

## Bounded next slice and proof

**CW2a, only after policy review:** add an internal unreachable pure stage-retirement/manifest module, proposed `src/central-recovery-stage.ts` plus its focused contract tests. It accepts an explicitly isolated, already copied staged store and trusted manifest input; no default database path, process/env secrets, root repair, network, service start or live caller. It emits a report including unsupported classes; incomplete means disabled. Small existing narrowing owners may need additive helpers in `store.ts`/authority modules after exact source ownership agreement. Do not wire it to `backup.ts`, `openStore`, CLI/server startup or advertise recovery readiness in this slice. No changes to CW1's reviewed source files are part of this document revision.

Next integration slice would necessarily touch `backup.ts`, `store.ts`, new root/exclusion modules and the live entry seams above, with source-specific review. A startup-only/root-metadata slice cannot enable remote TUI: complete retirement, exclusion, publication barrier and rollback manifest must land together. First enrollment is a separate explicit local action; existing personal installations are not silently enrolled by migration.

Focused isolated proof uses existing authority/backup test tables; no whole/import-selected suite and no real HOME/services/credentials:

- Negative compatibility: never-enrolled legacy/passwordless/SSO personal restores retain current behavior; metadata alone never enrolls.
- Classification: first enrollment faults before/after expectation publication, missing registry with central service binding, missing root, pre-enrollment DB rollback at enrolled path, copied/foreign DB, reinstall and explicit loss-of-root recovery. None self-heals into personal or central readiness.
- Mint → backup → revoke → staged retirement for ordinary API, MCP/OAuth access/refresh/used code, persisted cookie, lead, coordinator, remembered password and removed SSO subject. Exercise actual verifier refusal, not only counts/generation metadata.
- Stage repeat/crash/failure keeps originals unchanged and does not publish; each applicable manifest postcondition checked. Partial/unknown authority inventory prevents enabled report.
- Native integration later: competing direct CLI/server/MCP/worker starts, preexisting cached sessions, ingress callbacks, old nonparticipating binary, root symlink/FIFO/rename and lock inode contention. Prove stopped/excluded by actual owned process identity.
- Restored unattended approval/schedule/release/tool standing cannot act after fresh login; stale lease/upload/attempt cannot finalize or settle. Unknown stop remains unknown with no automatic failover.

No owner decision is required to preserve personal behavior and keep central recovery disabled. The selected expectation registry, service binding, cross-platform lock and complete authority manifest are engineering/review blockers, not permission to broaden product recovery policy.
